## Критично

### C-1. Мнемоника попадает в лог-файл и в интерфейс при опечатке во время импорта ✅

- **Где:** `mnemonic.rs:11-15`, `commands.rs:56` (`#[tracing::instrument(..., err)]`), `utils.rs:68-90`.
- **Суть:**
  - `coins-bip39 0.12.0` при несовпадении контрольной суммы возвращает `MnemonicError::InvalidPhrase(phrase)` с текстом ``the phrase `<вся фраза>` is invalid``. Это сверено по исходникам крейта на docs.rs.
  - `mnemonic::validate` вставляет этот текст в `format!("Invalid mnemonic: {e}")`.
  - Атрибут `#[instrument(err)]` на `create_wallet` пишет ошибку в лог на уровне ERROR.
  - В релизе лог пишется в `~/.satellion/logs/satellion.log` с правами 0644 и `Rotation::NEVER`.
  - Тот же текст возвращается во фронт и показывается пользователю.
- **Сценарий:** при импорте пользователь ошибается в одном слове, но это слово есть в словаре (UI проверяет только словарь, не контрольную сумму). В логе навсегда остаются 11 верных слов из 12. Двенадцатое подбирается перебором примерно из 12×2048 вариантов. Лог может прочитать любой процесс пользователя, а также другие локальные учётки.
- **Исправление:**
  - Возвращать общее сообщение «Invalid recovery phrase» и никогда не форматировать `e`.
  - Убрать `err` из `instrument` у команд, работающих с секретами.
  - Проверять контрольную сумму на фронте.
  - В релизе удалить или очистить существующий лог.

### C-2. Токен с символом «ETH» отправляет нативный эфир ✅🔹

- **Где:** `chain/eth/transfer_builder.rs:343-348` (`create_builder`), вызов на `:164-166`. Фронт: `src/routes/ethereum/view/Balances.svelte:54`.
- **Суть:**
  - Тип перевода выбирается по строке `token.symbol.to_uppercase() == "ETH"`.
  - Символ берётся из `symbol()` контракта при `track_token`, то есть его задаёт автор токена.
  - Для такого токена запускается `EtherTransferBuilder`: `to = recipient`, `value = parse_ether(amount)`. Адрес и decimals токена игнорируются.
  - Баланс проверяется по настоящему ETH, а экран подтверждения показывает «N ETH», так что подмену не видно.
- **Сценарий:** скам-аирдроп токена с `symbol() = "ETH"`. Жертва добавляет токен, ей говорят «верни токены, чтобы получить награду», и она отправляет N **настоящих** ETH.
- **Усугубляет:** кнопка «перестать отслеживать» скрыта у токена с символом ровно `'ETH'` (`Balances.svelte:54`), поэтому удалить фейк из интерфейса нельзя.
- **Исправление:**
  - Выбирать тип перевода по `token.address == constants::ETH.address` или через явный enum `TokenKind`.
  - В `track_token` отклонять адрес-сентинел и символы, совпадающие с ETH и токенами по умолчанию.
  - Кнопку удаления скрывать по адресу, а не по символу.

### C-3. В BTC получатель получает «сумма − комиссия», а экран показывает другое ✅🔹

- **Где:**
  - `chain/btc/tx_builder.rs:184-221` (`resolve_amounts`), `chain/btc/coin_selection.rs:9-35`, `chain/btc/account.rs` (Auto/Manual);
  - фронт: `src/routes/bitcoin/view_model/transfer.vm.svelte.ts:82-89`, `src/routes/bitcoin/view/TransferReview.svelte`.
- **Суть:**
  - Фронт передаёт `{ Auto: transfer_amount }`, то есть цель выбора монет — сумма **без** комиссии.
  - Knapsack сначала ищет подмножество UTXO с суммой ровно на цель.
  - Если оно нашлось, срабатывает `is_sweep = requested == total_input`, и комиссия вычитается из выхода получателя, а сдачи нет.
  - Бэкенд возвращает фронту только `{ fee }`. Экран строит «Сумма / Комиссия / Итого = сумма + комиссия» из собственного состояния.
- **Сценарий:** есть UTXO на 50 000 сат, пользователь оплачивает счёт на 50 000 сат. Экран показывает «50 000 + F», а получатель получает 50 000 − F, и счёт недоплачен. То же в ручном режиме, если сумма выбранных монет равна введённой.
- **Исправление:**
  - Сделать «отправить всё» явным флагом и не выводить его из равенства сумм.
  - Выбирать монеты под `amount + оценка комиссии`.
  - `build_tx` должен возвращать реальную разбивку (выходы, суммы, адреса сдачи, комиссию, входы), и экран подтверждения должен показывать только её.

### C-4. Создание кошелька молча затирает существующий файл

- **Где:** `wallet_keeper.rs:29-55`, `persistence.rs:88-104`, `persistence.rs:160-165` (`fs::write` без проверки существования), `persistence.rs:201-213` (`sanitize_filename`).
- **Суть:**
  - «My Wallet», «My_Wallet», «My.Wallet» и «My Wallet!» превращаются в один и тот же файл.
  - APFS по умолчанию не различает регистр, поэтому «Savings» и «savings» тоже совпадают.
- **Сценарии:**
  - У пользователя есть пополненный кошелёк «Savings». Он создаёт или импортирует «savings», и зашифрованная мнемоника старого кошелька пропадает с диска.
  - Открыт кошелёк «Main», пользователь создаёт новый «Main». Сессия старого при следующем `persist()` затирает файл нового. Новый кошелёк, который пользователь, возможно, уже пополнил, пропадает.
  - Новый кошелёк наследует запись в Keychain и историю в SQLite, потому что они привязаны к имени.
- **Исправление:**
  - Создавать файл через `OpenOptions::create_new(true)`.
  - Отклонять имена, которые после санитизации, приведения регистра и NFC-нормализации совпадают с существующими.
  - Лучше всего называть файлы случайным ID, а отображаемое имя хранить внутри шифротекста.

## Высокий риск

### H-1. На SegWit-адреса (BIP84) можно получить деньги, но нельзя их потратить ✅ *(предп.: поведение `Psbt::sign`)*

- **Где:** `chain/btc/tx_builder.rs:124-145`, `chain/btc/fee_bump.rs:101-114`, `chain/btc/key_derivation.rs:40-45,73`, `chain/btc/commands.rs` (`derive_external_address`), `chain/btc/discovery.rs`. Фронт: `src/routes/bitcoin/view/DeriveAddress.svelte:51` («SegWit (BIP84)»).
- **Суть:**
  - Интерфейс позволяет получить P2WPKH-адрес, а discovery сканирует пути BIP84. Такие UTXO попадают в баланс и в автовыбор.
  - PSBT заполняет только `tap_key_origins` и `tap_internal_key`. Поле `bip32_derivation` в коде не встречается ни разу.
  - Для P2WPKH-входа `Psbt::sign` ищет ключ в `bip32_derivation`, ничего не подписывает, и `finalize_mut` падает.
- **Сценарий:** пользователь получил деньги на SegWit-адрес или восстановил сид из Sparrow/Electrum. Любая отправка, в которую автовыбор взял такую монету, падает. Обычные платежи тоже ломаются случайным образом.
- **Дополнительно:** оценка размера входа 57,25 vB занижена для P2WPKH (нужно ~68 vB). Тестов на трату SegWit нет.
- **Исправление:**
  - Ветвиться по `derivation.purpose`: для P2WPKH заполнять `bip32_derivation` сжатым публичным ключом и считать вес входа по его типу.
  - Добавить e2e-тест на regtest.
  - Либо временно убрать SegWit из интерфейса и из discovery.

### H-2. Electrum-клиент рассинхронизируется после первого нового блока ✅🔹

- **Где:** `chain/btc/providers/electrum_client.rs:101-145, 268-274`, `chain/btc/providers/electrum_adapter.rs:45-58`.
- **Суть:**
  - `network_status()` вызывает `blockchain.headers.subscribe`, и фронт делает это при каждой загрузке. После этого сервер на каждый новый блок присылает уведомление в тот же сокет.
  - `recv()` читает одну строку на запрос и не сверяет `id`. Уведомление разбирается как ответ (ошибка «empty result»), а настоящий ответ остаётся в буфере.
  - Ошибка внутри batch оставляет непрочитанными остальные N ответов.
  - Соединение лежит в `OnceCell` и никогда не пересоздаётся.
- **Последствия:**
  - До конца сессии все ответы сдвинуты: UTXO приписываются не тем адресам и путям деривации, баланс и discovery врут, часть средств может быть пропущена.
  - `broadcast` может отправить транзакцию в сеть, но вернуть ошибку. Тогда путь сдачи не сохраняется, запись в БД не создаётся, и пользователь повторяет отправку.
- **Исправление:**
  - Сопоставлять ответы по `id`, а сообщения с полем `method` обрабатывать как уведомления.
  - При любой ошибке ввода-вывода или разбора пересоздавать соединение.
  - Не подписываться на заголовки без отдельного читателя уведомлений.

### H-3. Нет сетевых таймаутов, а запросы выполняются под глобальной блокировкой сессии 🔹

- **Где:**
  - все BTC- и ETH-команды делают `sk.lock().await` и затем ждут сеть: `chain/btc/commands.rs`, `chain/eth/commands.rs`, `commands.rs`;
  - таймаутов нет нигде: `TcpStream::connect`, `Socks5Stream::connect`, TLS-рукопожатие, `read_line` (`electrum_client.rs`), reqwest в `chain/eth/provider.rs`, esplora `Builder`;
  - монитор таймаута (`session/session_keeper.rs:95`) и обработчик блокировки экрана (`system/session_monitor/triggers.rs:23`) ждут тот же `tokio::Mutex`.
- **Сценарий:** сервер принял TCP-соединение и молчит. Команда зависает навсегда, интерфейс замирает. Пользователь блокирует экран или уходит, но `soft_terminate` стоит в очереди за зависшей командой. Расшифрованный кошелёк (сид, xprv) остаётся в памяти дольше таймаута и после блокировки ОС.
- **Дополнительно:** `read_line` без ограничения длины строки, и злонамеренный сервер может исчерпать память.
- **Исправление:**
  - Обернуть каждый connect, рукопожатие и чтение в `tokio::time::timeout`; задать `connect_timeout` и `timeout` в reqwest и `.timeout()` в esplora; ограничить длину строки.
  - Копировать нужные данные из сессии и отпускать `sk` до начала сетевого ввода-вывода.
  - Делать блокировку и истечение сессии через путь, который не может заблокироваться.

### H-4. Подготовленная ETH-транзакция глобальна и не привязана к подписанту ✅🔹

- **Где:** `main.rs:27,40` (один `Mutex<TxBuilder>` на всё приложение), `chain/eth/transfer_builder.rs:131-132,175-182,193-224`, `chain/eth/commands.rs` (`execute_transfer`).
- **Суть:**
  - `execute_transfer` подписывает `pending_tx` ключом аккаунта, который активен **сейчас**, и не сверяет его с `pending_meta.payload.sender`.
  - `discard_pending()` не вызывается нигде.
  - Подготовленная транзакция переживает смену аккаунта, блокировку, разблокировку другого кошелька и ошибки при повторной оценке.
- **Сценарий:** перевод подготовлен в аккаунте или кошельке A, затем пользователь переключился на B и отправил. Средства уходят с B с nonce и комиссией от A. Если nonce совпали (у новых аккаунтов он 0), транзакция проходит. История при этом смешивает A и B.
- **BTC-аналог (слабее):** `pending_tx` не сбрасывается при `switch_account`. Путь сдачи A записывается в keychain B, а у A сдача потом переиспользуется.
- **Исправление:**
  - Хранить pending-транзакцию в сессии вместе с именем кошелька, индексом аккаунта и адресом отправителя.
  - При отправке проверять совпадение.
  - Сбрасывать её при любой смене контекста и на путях ошибок.

### H-5. Chain id зашит как 1 и не сверяется с RPC ✅

- **Где:** `chain/eth/transfer_builder.rs:96,365,430`. Вызова `eth_chainId` нет нигде.
- **Суть:** RPC URL меняется в настройках. Если пользователь укажет Sepolia или L2, кошелёк всё равно подпишет транзакции для mainnet, но с nonce тестовой сети. У свежего аккаунта nonce 0 в обеих сетях, поэтому владелец RPC может переотправить такую транзакцию в mainnet и увести настоящий ETH. Адреса USDC/USDT и Chainlink тоже относятся к mainnet.
- **Исправление:** при старте и перед подписью сверять `eth_chainId` и отказываться работать при несовпадении.

### H-6. Режим Tor пропускает трафик мимо Tor ✅🔹

- **Где:** `chain/btc/fee_estimator.rs:24-55`, `chain/btc/providers/btc_node.rs:15-21`, `config/config_impl.rs:27`, `chain/eth/provider.rs:24-31`.
- **Суть:**
  - При включённом Tor `select_btc_server` всё равно возвращает `BtcNode::Electrum`, а ветка `Esplora` не создаётся нигде. Поэтому `estimate_fee_rate` при **каждом** `build_tx` идёт напрямую на `https://mempool.space/api`: DNS через системный резолвер и TCP с реального IP за секунды до отправки. Комментарий в коде про «Esplora/Tor path» устарел.
  - ETH ходит через `socks5://`. В reqwest 0.13 это означает локальный DNS (`connect.rs:540-541`), так что имя RPC утекает провайдеру, а `.onion` RPC не работает.
  - Если вручную поставить `socks5h://`, ломается BTC: `electrum_client.rs` и `tor.rs` срезают только префикс `"socks5://"`.
  - Свой Electrum-сервер в режиме Tor молча игнорируется.
  - Ссылки на mempool.space и etherscan открываются в системном браузере мимо Tor.
- **Исправление:**
  - В режиме Tor брать оценку комиссии у Electrum через Tor или вести Esplora через прокси.
  - По умолчанию использовать `socks5h://` и разбирать URL прокси через `url::Url`.
  - Учитывать свой сервер в режиме Tor.
  - Предупреждать о ссылках на обозреватели.

### H-7. Кнопка «Lock» блокирует только интерфейс ✅

- **Где:** `src/components/Navbar.svelte:27-31`. В `codegen.rs` нет команды, завершающей сессию.
- **Суть:** `lock()` сбрасывает Svelte-сторы и переходит на экран разблокировки, но кошелёк остаётся расшифрованным в `SessionKeeper` до таймаута (по умолчанию 30 минут) или блокировки экрана ОС. Всё это время через IPC доступны `build_tx` → `broadcast_tx` и `estimate_transfer` → `execute_transfer` без пароля.
- **Исправление:** добавить команду `lock_wallet` → `sk.terminate()` и вызывать её из `lock()` и при открытии экрана разблокировки.

## Средний риск

### M-1. Слабая защита файла кошелька

- **Где:** `config/constants.rs:4`, `commands.rs:65`, `persistence.rs:163`, `db.rs:16-27`, `config/config_impl.rs:99,110,145`, `utils.rs:74-76`.
- **Суть:**
  - Минимальная длина пароля — 4 символа. На бэкенде её проверяют только при генерации нового кошелька, при импорте минимума нет. UI требует минимум везде, но это обходится через IPC.
  - Пароль от файла по умолчанию одновременно служит BIP39-паролем («25-м словом»). Сменить его нельзя без переноса средств. Пользователь, записавший только 12 слов, без пароля средства не восстановит.
  - Права на файлы и папки 0644/0755. Домашняя папка на macOS по умолчанию читаема для других локальных пользователей, поэтому зашифрованные файлы можно унести и перебирать офлайн. Argon2 с 64 МБ не спасает четырёхсимвольный пароль.
  - Пароль не нормализуется по NFKD перед Argon2.
- **Исправление:**
  - Минимум 10–12 символов на бэкенде для обоих сценариев.
  - Права 0700 на папки и 0600 на файлы.
  - Явное предупреждение о связке «пароль = BIP39 passphrase».
  - Нормализовать пароль один раз при вводе.

### M-2. Неатомарная запись единственной копии ключа

- **Где:** `persistence.rs:160-165`. `persist()` вызывается почти на каждой команде: `get_wallet_balance`, `sync_utxos`, `switch_account`, `switch_blockchain`, `discover_wallet`, `derive_external_address`, `broadcast_tx`.
- **Суть:** truncate-и-запись через `fs::write`. Падение приложения, отключение питания или полный диск во время записи портят зашифрованную мнемонику. То же для `config.json`.
- **Исправление:**
  - Писать во временный файл, затем `fsync` и `rename`, затем `fsync` каталога.
  - Сохранять только при реальных изменениях.
  - Держать резервную копию `.bak`.

### M-3. Глобальный флаг `omit_passphrase_on_private_key` и молчаливый откат конфига ✅

- **Где:** `config/config_impl.rs:33-52, 63-92, 148-154`; используется в `chain/btc/wallet.rs:67` и `chain/eth/wallet.rs:86`.
- **Суть:**
  - Флаг один на все кошельки и не хранится в файле кошелька. Переключение меняет все адреса всех кошельков: балансы выглядят пустыми, новые адреса приёма принадлежат другой деривации.
  - UI требует пароль от 4 символов даже при импорте. Поэтому обычную мнемонику без BIP39-пароля корректно импортировать можно только через этот глобальный флаг, а он ломает остальные кошельки.
  - Если `config.json` не разобрался (например, обрезался при неатомарной записи), приложение молча берёт настройки по умолчанию: Tor выключен, флаг выключен. Следующий `set_config` перезапишет файл пользователя.
  - У `ConfigSecurity` нет `#[serde(default)]`. Добавление нового поля сломает разбор всех существующих конфигов.
  - Это уже случалось: коммит `9625a67` перенёс `omit_passphrase_on_private_key` в `security.*` без миграции, и у пользователей значение молча сбросилось.
- **Исправление:**
  - Хранить флаг для каждого кошелька внутри шифротекста и выбирать его при создании или импорте.
  - Если конфиг не разобрался, останавливаться и показывать ошибку (fail-closed).
  - Добавить версионирование и миграции конфига.

### M-4. `set_config` не проверяет значения и работает без сессии

- **Где:** `commands.rs:346-356`, `chain/btc/config.rs:10-11`, `chain/eth/config.rs:14-15`, `chain/eth/provider.rs:21,25,30`.
- **Суть:**

- **Исправление:**
  - Проверять значения на бэкенде: `https` или `.onion` для RPC, SOCKS только на loopback, ограничение диапазона таймаута.
  - Исключить `regtest` и `anvil` из релизной сборки.
  - Требовать сессию и пароль для Tor, флага пароля и смены серверов.
  - Заменить `expect` на обработку ошибок.

### M-5. Touch ID проверяется только приложением; пароль остаётся в Keychain после отключения и удаления кошелька

- **Где:** `system/biometric/keychain.rs:34-52`, `system/biometric/prompter.rs`, `commands.rs:247-295, 320-332`; фронт: `src/view_model/biometric.svelte.ts:47,62,87`, `src/view_model/wallet.svelte.ts:20`.
- **Суть:**
  - Запись создаётся без `SecAccessControl` (`biometryCurrentSet`), в устаревшем файловом login keychain. `LAContext` не передаётся в чтение. Touch ID здесь — просто проверка внутри приложения.
  - Подпись ad-hoc (`signingIdentity: "-"`), поэтому ACL Keychain завязан на хеш бинарника, который меняется с каждой сборкой. Это приучает пользователя нажимать «Always Allow». *(предп.)*
  - **Несовпадение ключей:** `enable_biometric_unlock` сохраняет запись под исходным `wallet.name` («My Wallet»). `is_enabled`, `disable`, `forget` и разблокировка работают с именем из `get_wallets`, а это санитизированное имя файла («My_Wallet»). В итоге UI показывает биометрию выключенной, «Отключить» и «Забыть кошелёк» ничего не удаляют, и пароль остаётся в Keychain навсегда.
  - Включение Touch ID не требует повторного ввода пароля.
  - `store` сначала удаляет запись и только потом добавляет новую, поэтому сбой добавления теряет привязку.
- **Исправление:**
  - Подписывать сборку Team ID и использовать data-protection keychain с `SecAccessControl(.biometryCurrentSet)` и передачей аутентифицированного `LAContext`.
  - Использовать единый ключ — UUID кошелька.
  - Требовать пароль при включении Touch ID.

### M-6. `forget_wallet` удаляет любой кошелёк без сессии и пароля

- **Где:** `commands.rs:317-332`, `src/routes/settings/ForgetWallet.svelte`.
- **Суть:** команда принимает произвольное `wallet_name`. Один клик в модальном окне — и файл удалён, без пароля и без вопроса «сохранена ли фраза». Заодно закрывается текущая сессия, даже если удаляется другой кошелёк. `disable_biometric_unlock` тоже работает без сессии.

### M-7. Нет потолков комиссий; CPFP отправляется без подтверждения

- **Где:** `chain/btc/fee_estimator.rs:43-48`, `chain/btc/tx_builder.rs:194`, `chain/btc/fee_bump.rs:51-59`, `chain/btc/commands.rs` (`bump_fee_cpfp`), `chain/eth/fee_estimator.rs:74-103`, `chain/eth/transfer_builder.rs:231-253`, `chain/eth/price_feed.rs`. Фронт: `src/routes/bitcoin/view/FeeBump.svelte`.
- **Суть:**
  - **BTC:** ставка от mempool.space или Electrum принимается без верхней границы. Единственный неявный потолок — 25 000 sat/vB в `extract_tx()`. *(предп.)*
  - **CPFP:** собирается, подписывается и отправляется одним шагом. Ставка с фронта не проверяется на верхнюю границу, нет проверки на пыль, нет проверки, что родитель ещё не подтверждён. Опечатка 500 вместо 5 sat/vB уходит в сеть сразу.
  - **ETH:**
    - priority fee — медиана из `fee_history` от RPC, без потолка;
    - gas limit берётся из `eth_estimateGas` как есть, без потолка и без запаса;
    - курс Chainlink читается через тот же RPC без проверки `updatedAt`, `answeredInRound` и `answer > 0`. Злонамеренный RPC может завысить комиссию и одновременно занизить курс, чтобы «$0.40» её скрывало.
- **Исправление:**
  - Жёсткие потолки: sat/vB; priority fee; `maxFee ≤ k × baseFee`; gas ≤ 21000 для ETH-перевода на EOA и ≤ ~150k для ERC-20.
  - Предупреждение, если комиссия больше X% от суммы.
  - Для CPFP — шаги «собрать → показать → HoldToSend».
  - Проверять свежесть данных Chainlink.

### M-8. Экран подтверждения ETH показывает слишком мало; адреса не проверяются по контрольной сумме

- **Где:** `src/routes/ethereum/view/Transfer.svelte:69-71,119-139`, `commands.rs:47-49`, `chain/eth/wallet.rs:202-204`.
- **Суть:**

  - `Address::from_str` не проверяет EIP-55 *(предп.)*: опечатка в адресе со смешанным регистром принимается.
  - Нет запрета на нулевой адрес, на адрес контракта самого токена (токены сгорят) и предупреждения об отправке самому себе.
- **Исправление:**
  - Показывать в подтверждении данные, которые вернул бэкенд из pending-транзакции.
  - Использовать `Address::parse_checksummed` для ввода со смешанным регистром.
  - Добавить запреты и предупреждения выше.

### M-9. Мнемоника остаётся в буфере обмена и в памяти

- **Где:** фронт: `src/routes/wallet/create/create_flow.svelte.ts:58-65,91-97`, `GeneratePhrase.svelte:11-18`. Бэкенд: `persistence.rs:54,82,91`, `chain/btc/wallet.rs:25-29,63-71`, `chain/eth/wallet.rs:79-90`, `commands.rs:72-81`.
- **Суть:**
  - Фразу можно скопировать кликом, и буфер обмена потом не очищается (clipboard-менеджеры, Universal Clipboard).
  - На каждом сохранении мнемоника клонируется в обычный `String`, сериализуется в JSON и при загрузке лежит в `Vec`, ничего из этого не обнуляется. Это обесценивает `SecretBox`.
  - 64-байтный сид, chain code и дочерние ключи не обнуляются. `coins-bip39` не реализует `Zeroize`.
  - `create_wallet` при ошибке выходит через `?` до `zeroize()`.
  - Нет защиты окна от скриншотов (`contentProtected`).
- **Исправление:**
  - Убрать копирование фразы или очищать буфер по таймеру.
  - Использовать `Zeroizing<String>` и `Zeroizing<Vec<u8>>`, сериализовать в заранее выделенный `Zeroizing`-буфер, обнулять сид.
  - Включить фичи `zeroize` в `aes-gcm` и `argon2`.

### M-10. История транзакций в SQLite хранится открытым текстом и не удаляется

- **Где:** `~/.satellion/blockchain.db`, `migrations/*/up.sql`, `repository/tx_repository.rs`.
- **Суть:**
  - Имя кошелька, адреса отправителя и получателя, суммы и время доступны без пароля, и по ним видна связь с on-chain-личностью.
  - При удалении кошелька история остаётся, при переименовании теряется, а новый кошелёк с тем же именем её наследует.
  - `tx_hash` — глобальный первичный ключ, поэтому перевод между двумя своими кошельками не записывается: ошибка вставки игнорируется.
  - В ETH-истории комиссия всегда равна `i32::MAX` (2147483647), а сумма ограничена ~9,22 ETH.
- **Исправление:** привязывать записи к ID кошелька, удалять и мигрировать их вместе с кошельком, хранить суммы строками, по возможности шифровать.

### M-11. CSP выключена, isolation-хук ничего не делает

- **Где:** `src-tauri/tauri.conf.json` (`"csp": null`), `dist-isolation/index.js` (`payload => payload`), `src-tauri/capabilities/default.json` (`opener:default`).

  - подтверждение (HoldToSend) существует только в JS;
  - `set_config` перенаправляет серверы;
  - `forget_wallet` удаляет кошельки.
- **Исправление:**
  - Строгая CSP: `default-src 'self'; script-src 'self'; connect-src ipc: http://ipc.localhost; img-src 'self'; style-src 'self' 'unsafe-inline'`.
  - Allowlist команд и аргументов в isolation-хуке.
  - Сузить opener до двух обозревателей.
  - В идеале — нативное подтверждение транзакции на стороне Rust.

### M-12. Цепочка поставки и релизы

- **Где:** `.github/workflows/publish.yml`, `src-tauri/tauri.conf.json`, `readme.md`.
- **Суть:**

  - Job сборки имеет `contents: write`, а `persist-credentials` по умолчанию включён. Токен с правом переписать релизы доступен всем `build.rs` и proc-macro примерно 830 крейтов, а также установке npm-пакетов.

  - Нет механизма обновлений.
  - Версии расходятся: `package.json` 0.3.0, а `tauri.conf.json` и `Cargo.toml` 0.2.0.
- **Исправление:**

### M-13. Злонамеренный или сломанный Bitcoin-сервер

- **Где:** `chain/btc/discovery.rs:188-223`, `chain/btc/commands.rs` (`broadcast_tx`), `chain/btc/coin_selection.rs`, `chain/btc/providers/electrum_adapter.rs:91-136`.
- **Суть:**
  - **Бесконечный discovery:** если сервер на любой адрес отвечает «есть история», цель сканирования всё время сдвигается, и сканирование идёт до 2³¹ под локом сессии.
  - **Нет SPV:** балансы, UTXO и подтверждения принимаются на веру. Сервер может показать фейковый «подтверждённый» входящий платёж. Taproot защищает от подмены сумм при подписи; после исправления H-1 для P2WPKH это уже будет не так.
  - **Потраченные входы не помечаются локально:** повторная отправка сразу после первой может взять те же монеты, и с RBF вторая транзакция заменит первую.
  - **Выбор монет:**
    - largest-first покрывает только цель без комиссии: при UTXO [100 000, 5 000] отправка 99 990 даёт «недостаточно средств»;
    - knapsack предпочитает точное совпадение даже из сотни пыльных входов, а это огромная комиссия, которая по C-3 вычитается из суммы получателя;
    - DP занимает до ~40 МБ и выполняется под локом;
    - `Auto(u32)` ограничивает отправку ~42,9 BTC.
  - **txid от Electrum не сверяется с `compute_txid()`.**
- **Исправление:**
  - Жёсткий потолок индексов discovery.
  - Проверка merkle-доказательств.
  - Блокировать потраченные outpoint после отправки.
  - Branch-and-bound по эффективным значениям в `spawn_blocking` и `u64`.
  - Сверять txid.

### M-14. Неверные индексы и переключения

- **Где:** `commands.rs:126-139`, `chain/btc/wallet.rs:117-122,138-140`.
- **Суть:** BTC `switch_account` принимает любой индекс без проверки и сохраняет его. После этого `active_account()` возвращает «account not found», и `do_unlock` падает: кошелёк больше не открывается без ручной правки зашифрованного файла. В ETH индекс проверяется.
- **Исправление:** проверять индекс так же, как в ETH.

### M-15. Сессия и Tor-процесс

- **Где:** `session/session_keeper.rs:52-60,87-106`, `system/tor.rs`, `system/session_monitor/*`.
- **Сессия:**
  - `session()` не проверяет `is_expired()` и продлевает её, поэтому в течение примерно минуты после таймаута сессию можно «воскресить» любой командой.
  - Таймаут считается по системным часам.
  - Отслеживается только `com.apple.screenIsLocked`; сон без блокировки и быстрая смена пользователя не обрабатываются.
  - На Linux, который собирается в CI, блокировка экрана не отслеживается совсем.
  - События `session-locked/unlocked` — обычные глобальные события Tauri, и JS может их эмитить (это только DoS).
- **Tor:**
  - `tor` запускается по `PATH`, а у приложения, запущенного из Finder, Homebrew-путей в PATH нет. *(предп.)*
  - Если запуск не удался, приложение только пишет в лог. Готовность Tor проверяется по «порт слушается», а порт может занять любой локальный процесс.
  - UI не показывает статус Tor.
  - ETH-провайдер создаётся один раз при старте, BTC — при каждой разблокировке, так что включение и выключение Tor применяется неравномерно.
- **Исправление:**
  - Проверять истечение сессии при каждом доступе; хранить таймаут на монотонных часах.
  - Обрабатывать сон; добавить logind/D-Bus для Linux.
  - Указывать абсолютный путь к Tor или встроить arti; проверять bootstrap Tor; показывать статус в UI.

## Низкий риск

- **L-1.** Паники от входных данных:
  - `.expect("pending tx not found")` в `chain/btc/commands.rs` (`broadcast_tx`) при повторном вызове;
  - `.unwrap()` на невалидном txid в ручном выборе монет (`chain/btc/account.rs:192-196`);
  - `BlockChain::from(u16)` паникует на неверном значении (`config/constants.rs:17`);
  - `HOME` через `expect` (`config/config_impl.rs:120`).
- **L-2.** Сдача меньше 330 сат уходит майнерам и не учитывается в показанной комиссии. На выход получателя нет проверки на пыль.
- **L-3.** Ручной выбор монет: дубли outpoint не устраняются, и их сумма удваивается, что даёт невалидную транзакцию. Отсутствующие outpoint молча выбрасываются.
- **L-4.** Тестовая команда `anvil_set_initial_balances` зарегистрирована в релизе (`codegen.rs:120`) и отправляет `anvil_*` с адресом пользователя на публичный RPC.
- **L-5.** Nonce в ETH, вероятно, читается по `latest`, а не по `pending` *(предп.)*: вторая отправка до майнинга первой получает тот же nonce.
- **L-6.** ETH:
  - `fee_ceiling` в gwei насыщается выше ~18,4 ETH;
  - `parse_units(...).get_absolute()` превращает «-5» в 5 (на фронте это блокируется);
  - лишние знаки после запятой, вероятно, молча обрезаются *(предп.)*;
  - `max_fee - priority` без `saturating_sub`;
  - у gas limit нет запаса.
- **L-7.** Один «сломанный» отслеживаемый токен валит весь баланс, включая ETH, и удалить его из интерфейса нельзя. Токены с `bytes32 symbol` не добавляются. Возврат `transfer()` не проверяется.
- **L-8.** Имена кошельков, которые после санитизации становятся пустыми («🔥», «...»), дают скрытый файл `.satellion`: кошелёк исчезает из списка, а следующие такие имена его затирают.
- **L-9.** Переименование не транзакционно: при сбое на диске остаются две зашифрованные копии.
- **L-10.** В формате файла не учитывается `version`, параметры Argon2 не хранятся и не аутентифицируются как AAD. Кошелёк из debug-сборки (Argon2 512 КБ) не откроется в релизе.
- **L-11.** Курс USD берётся один раз при разблокировке; если запрос не удался, показывается «$0». Индикатор Tor в навбаре отражает несохранённое состояние.
- **L-12.** Gap limit: адреса с индексом за пределами 20 от последнего использованного не найдутся при восстановлении из сида.
- **L-13.** Log без ротации; при `RUST_LOG=debug` в лог пишется весь конфиг, включая ключ API в `rpc_url`, если он там есть.

## Info

- ETH-деривация `m/44'/60'/{account}'/0/0` (схема Ledger Live). Аккаунт 0 совпадает с MetaMask, аккаунты 1+ — нет.
- BTC: сдача всегда выход 0 и всегда Taproot, `locktime = 0` — это отпечаток кошелька. Все адреса запрашиваются одним батчем у одного сервера и связываются между собой.

## Что сделано хорошо

- **AES-256-GCM и Argon2id** (64 МиБ, t=3, p=1); при каждом сохранении свежие случайные DEK, nonce и соль; проверка тегов на обоих слоях; длины проверяются до `split_at`.
- **Мнемоника** генерируется из 128 бит `OsRng`.
- **Логи:** `skip_all` на всех командах, других утечек секретов в логах нет (кроме C-1).
- **История git:** секретов нет ни в одном из 244 коммитов. Встречаются только публичный ключ Anvil и тестовый вектор «abandon … about».
- **Фронт:**
  - нет `{@html}`, `innerHTML`, `eval` и удалённых ресурсов;
  - devtools только в debug;
  - в localStorage хранится только тема.
- **Создание кошелька:** перед созданием пользователь подтверждает 3 случайных слова фразы; секреты очищаются при уходе с экрана; поля ввода секретов — `type=password`, без autocomplete и spellcheck.
- **HoldToSend:** 3 секунды непрерывного удержания с корректной отменой.
- **Taproot PSBT:** `witness_utxo` на всех входах; sighash BIP341 коммитит суммы, поэтому сервер не может обмануть с комиссией через подмену сумм.
- **Electrum:** TLS проверяется по webpki-roots с SNI; через Tor DNS резолвится удалённо.
- **Пути и SQL:** обход путей через имя кошелька невозможен; SQL только через Diesel DSL.
